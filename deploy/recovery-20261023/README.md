# 2026-10-23 数据迁移与恢复部署

本次基于上游 `1c995081c45dd465877c4f6ecbf313490baa8820`（0.9.30），使用 iii-engine / iii-sdk 0.22.1。原来部署的 0.9.29 私有补丁仅把大表拆成 256 个 `rows` 对象；整表列表调用仍汇总全部数据，旧引擎被 OOM 杀死后，存活的 Node 进程又使容器无法触发自动重启。

## 数据与存储

- 迁移程序用与引擎相同的 rkyv 结构读取文件，严格校验旧分片路由、重复键和原生/分片冲突。
- 四个大范围迁移为 1024 个原生分区，记录的键和内容保持不变。每条记录先在新文件中复读，之后导入 Redis，再逐条复读比对。
- `AGENTMEMORY_PARTITIONED_SCOPES` 必须与 `mem:storage:layouts` 中已完成的迁移标记匹配；缺失或不匹配直接报错。
- 线上状态访问继续走 iii-engine 的官方 Redis 适配器；离线工具只用于停止写入期间的格式转换和导入。
- 图索引复用上游 `projectGraphIndexRecord`，在磁盘上排序倒排成员，避免在线逐条 RPC 建索引。生成结果通过上游读取、改名、删除的兼容测试；记录和索引均进行全量导入复读验证。
- Redis 使用 AOF、每秒 fsync、`noeviction` 和 10 GiB 数据上限。容器上限分别为应用 8 GiB、Redis 14 GiB，不对主机发布 Redis 端口。
- 历史快照目录继续使用原来的挂载。原始数据、镜像及完整服务目录备份保持独立，不能用迁移后的目录覆盖回滚数据。

## 查询与恢复

insights 列表、搜索、衰减和诊断逐分区处理；前两者只保留有界的最佳结果。新生成的概念簇最多 64 个概念，单簇证据最多 64 条事实、32 条经验和 16 条工作总结，来源 ID 只记录模型实际引用的记录。历史记录不截断。

`supervisor.mjs` 直接管理引擎和 worker。任一进程退出会结束整个容器；健康探测持续失败也会结束容器，由 Docker 重启策略恢复。正常停机先让 worker 退出，再关闭引擎，并设硬退出期限。健康探测认可 CPU 繁忙但连接与存储正常的 503，避免压力下误重启。

独立运行目录 `/data/runtime-redis-v22` 用于避开上游状态模块读取旧默认配置的行为；必须确认实际图索引 buildId、后端与新部署一致。镜像保留中文 Jieba 原生分词组件。

入口 Nginx 保留既有令牌校验，并使用 `proxy_set_header Authorization $http_authorization;` 将已校验的凭据传给应用。旧配置清空这个请求头，会导致新版应用返回 401。代理配置修改前保留备份，检查通过后再重新加载。

根目录 `package-lock.json` 固定此次构建的依赖解析结果；上游忽略该文件，本次显式纳入版本控制，未修改忽略规则。

## 文件说明

- `migrate/`：旧分片解码、原生分区生成和 JSONL 导出；Cargo.lock 固定工具依赖。
- `build-graph-index.ts`：离线投影及排序后的倒排链表生成。
- `redis-migrate.py`：导入和逐条复读；读取服务器私有 Redis 配置，不输出凭据。
- `acceptance.py`：真实查询负载、验证记录持久化、引擎 SIGKILL、worker SIGSTOP、Redis SIGKILL 和验证记录清理。
- `compose.yaml`：生产编排模板，复制到服务根目录后使用；私有环境文件位于该目录的 `secrets/`，不进入仓库。

## 验证与边界

自动化测试覆盖分区路由、缺失布局拒绝读取、惰性扫描、固定图代次、离线索引的读写兼容、衰减并发与健康策略。实际验收报告记录全套测试、请求延迟、内存采样、重启次数及恢复时长。

后台日常路径已消除 insights 整表汇总；显式全量导出等管理操作仍可能占用较多内存。有限时长的压力测试不能证明未来永不增长，生产依靠资源边界、持久化、日志轮转和实际存活探测来限制影响并恢复。

回滚前先关闭入口并停止新服务，备份上线后的 Redis 增量，再恢复升级前的 compose 和数据。旧版本无法读取新 Redis/分区布局，不应直接把旧镜像指向新数据。不要停止或修改其他服务。
